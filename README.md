## Problem
Students waste time looking for seats at peak hours, library zones are used unevenly,
and demand for books is hard to plan. This system forecasts zone-level occupancy
(1 and 4 hours ahead), flags crowded hours, recommends less-crowded alternative zones,
forecasts weekly book demand by category, and explains every forecast.

**Users:** students (where and when to study) and library administrators (peak hours, resource planning).
**ML task:** regression on occupancy rate (occupancy / capacity); peak detection by thresholding the forecast
(rate >= 0.70 is a peak hour); a separate regression for books borrowed per category 7 days ahead.
**Success criteria:** beat naive and seasonal baselines on a chronological test set, with high recall on peak hours.

## Data
No real library logs were available, so the data is **synthetic**, generated by `src/data_generation.py`:
2 years (Jul 2024 - Jun 2026) of hourly occupancy for 4 zones (Reading Hall, Silent Study, Computer Lab,
Group Discussion), 40,880 rows, plus daily book borrowing for 6 categories.
It models two daily peaks per zone, weekday effects, holidays, vacations, exam periods with a pre-exam ramp-up,
autocorrelated noise, random outage/event days, 0.5% missing readings and 0.1% impossible sensor readings.
Calendar dates (holidays, exam windows) are assumptions. Because the generating process is known,
accuracy here is likely higher than it would be on real sensor data.

## Approach
| Stage | What was done |
|---|---|
| EDA | `notebooks/01_eda.ipynb`: distributions, hourly/weekly patterns, exam effect, outliers, autocorrelation, class imbalance |
| Preprocessing | readings above capacity set to missing, forward-filled within zone (past values only); target = occupancy rate |
| Features | calendar flags, days to exam, cyclic hour/weekday, lags (previous slot, same hour yesterday, same hour last week), rolling means; all lags shifted by the forecast horizon |
| Split | chronological: train 2024-07 to 2025-12 (30,352 rows), validation 2026-01 to 2026-03 (5,040), test 2026-04 to 2026-06 (5,096); no shuffling; leakage test in `src/check_leakage.py` |
| Models | 3 baselines (persistence, same hour last week, historical average), Ridge, Random Forest, XGBoost, LightGBM |
| Optimization | Optuna (30 trials, time-aware CV) for LightGBM and XGBoost; stacking ensemble with out-of-fold predictions |
| Evaluation | MAE, RMSE, R2, peak precision/recall/F1; error analysis by zone, hour, period and worst days |
| Explainability | SHAP (global, dependence and local waterfall plots) |
| Extra modules | peak-hour windows, alternative-zone recommender, book demand forecast |
| Deployment | Streamlit app on Streamlit Community Cloud |

## Results (held-out test set)
| Horizon | Model | MAE | R2 | Peak recall / precision |
|---|---|---|---|---|
| 1 hour | Tuned LightGBM | 0.0182 | 0.987 | 0.908 / 0.913 at threshold 0.70 |
| 1 hour | Persistence baseline | 0.0562 | 0.852 | 0.772 / 0.771 |
| 4 hours | Tuned LightGBM | 0.0264 | 0.970 | 0.848 / 0.859 at threshold 0.70 |
| 4 hours | Persistence baseline | 0.1733 | 0.044 | 0.320 / 0.318 |

- **Alert threshold** (chosen on validation, F2 score): 0.65 at 1 hour gives peak recall 0.982 with precision 0.775;
  0.60 at 4 hours gives recall 0.986 with precision 0.660. Missing a crowded hour costs more than a false alarm.
- **Stacking** gave no clear gain over tuned LightGBM (validation MAE 0.0249 vs 0.0250 at 1 hour; worse at 4 hours),
  so the simpler single model was kept.
- Half of the test rows are vacation days, which are easy; on regular days MAE is about 0.028 and on exam days about 0.030 (1 hour).
- **Book demand** (7 days ahead): test WAPE 12.9%, MAE 4.3 books/day vs 9.4 for "same weekday last week".
  The remaining error is mostly Poisson noise in the data.
- **Recommender:** 617 alerts on test; an alternative was available for 46.8%, and 99.3% of those were genuinely below 70% full.

## Explainability
At a 1-hour horizon the latest reading dominates (recent history is about 78% of total SHAP importance).
At 4 hours the same hour last week and yesterday, plus the vacation flag, take over and the calendar's share rises from about 5% to about 24%.
The further ahead we forecast, the more the model relies on routine instead of momentum.

## Limitations
- Synthetic data: real sensor data would be noisier and accuracy lower.
- Occupancy is capped at capacity, so demand above the seat count is invisible (censored data).
- Random outage/event days cannot be predicted from the features.
- Persistence is a weak baseline for 4-hour forecasts because the library closes overnight.
- SHAP explains what the model uses, not what causes crowding; correlated lags share credit.
- Alternative zones are a domain assumption; the Computer Lab has no substitute.

## Run it yourself
```bash
git clone https://github.com/ravikumartechie/smart-library-occupancy.git
cd smart-library-occupancy
python -m venv venv && venv\Scripts\activate
pip install -r requirements-dev.txt          # full training stack
python src/data_generation.py                # synthetic data -> data/raw
python src/features.py && python src/features.py 4
python src/train.py && python src/tune.py    # add 4 for the 4-hour horizon
python src/evaluate.py && python src/explain.py
python src/resources.py && python src/recommend.py
streamlit run app/streamlit_app.py
```
`requirements.txt` holds the pinned dependencies used by the deployed app.
